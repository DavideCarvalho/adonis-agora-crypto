A tenant presents a bearer token. The server verifies it and derives **the app and the
capabilities from the token**, never from the request. This is the same contract as
`@adonis-agora/durable`, `@adonis-agora/flags` and `@adonis-agora/config`: one authkit *service
tenant* client can hold several resources.

## With authkit

Register the app in authkit as a service tenant (the `client_credentials` grant) for the resource
`urn:agora:crypto`, with the scopes it needs:

```
resource: urn:agora:crypto
scope: crypto:encrypt:media
       crypto:decrypt:media
       crypto:sign:webhooks
       crypto:keys:read        # the console, the CLI, the audit trail
```

```ts title="config/crypto.ts (the server)"
import { authkitTenantVerifier } from '@adonis-agora/authkit-client'
import { defineConfig } from '@adonis-agora/crypto'

export default defineConfig({
  topology: 'control-plane',
  verifyTenant: authkitTenantVerifier({
    issuer: env.get('AUTHKIT_ISSUER'),
    resource: 'urn:agora:crypto',
  }),
})
```

```ts title="config/crypto.ts (an app)"
import { authkitTenantToken } from '@adonis-agora/authkit-client'

export default defineConfig({
  topology: 'tenant',
  tenant: {
    url: env.get('CRYPTO_URL'),
    partition: 'streaming',
    token: authkitTenantToken({
      issuer: env.get('AUTHKIT_ISSUER'),
      clientId: env.get('AUTHKIT_CLIENT_ID'),
      clientSecret: env.get('AUTHKIT_CLIENT_SECRET'),
      resource: 'urn:agora:crypto',
    }),
  },
})
```

Tokens are verified locally against the issuer's JWKS, found through discovery
(`/.well-known/openid-configuration` → `jwks_uri`). No hard-coded token URL, no call per request.
authkit-server is never required in the server's process.

## Without authkit

One shared secret per app, compared in constant time. The app names itself with `x-crypto-app`; the
secret proves it.

```ts
export default defineConfig({
  topology: 'control-plane',
  verifyTenant: sharedSecretVerifier({
    partitions: {
      streaming: {
        secret: env.get('CRYPTO_SECRET_STREAMING'),
        capabilities: ['crypto:encrypt:media', 'crypto:decrypt:media'],
      },
      // A string means the default: ['crypto:*'].
      billing: env.get('CRYPTO_SECRET_BILLING'),
    },
  }),
})
```

`sharedSecretVerifier` also accepts a `actor`, recorded in the audit trail when the credential is
used by an automation (`actor: 'agent:7'`).

## Capabilities

| Capability | Grants |
| --- | --- |
| `crypto:encrypt:<key>` | `encrypt` on that key |
| `crypto:decrypt:<key>` | `decrypt` on that key |
| `crypto:rewrap:<key>` | `rewrap` (also needs `encrypt` and `decrypt` on it) |
| `crypto:datakey:<key>` | `generateDataKey` (also needs `encrypt`/`decrypt`) |
| `crypto:sign:<key>` | `sign` |
| `crypto:verify:<key>` | `verify` |
| `crypto:hmac:<key>` | `hmac` |
| `crypto:keys:read` | list keys, read metadata and versions, audit trail, public keys |
| `crypto:keys:manage` | create, rotate, change policy, delete |
| `crypto:keys:export` | export an `exportable` key's material |
| `crypto:seal:<key>` | `encrypt` with `<key>` of **another** partition ([sealing for another partition](#sealing-for-another-partition)); never decrypt. Only an explicit grant counts: `crypto:*` does not |

`*` matches one segment, and a trailing `*` matches everything after it:

| Written | Matches |
| --- | --- |
| `crypto:*` | everything |
| `crypto:encrypt:*` | `encrypt` on every key |
| `crypto:*:media` | every operation on `media` |

Nothing is implied: `crypto:encrypt:media` cannot decrypt, and `crypto:keys:read` grants no
operation. In the key-name segment, a prefix ending in `*` matches key names starting with it:
`crypto:decrypt:console-*` opens `console-crypto`, `console-flags`, … and nothing else.

## Sealing for another partition

A token's partition is the only one it touches, with one exception: `encrypt` may name another
partition, so one app can write something only that other app can read. The Agora consoles use it
to seal commands for the apps they manage (`console-<lib>` keys) when the crypto server is a
separate app.

```ts
// The console's client: its token is for its own partition ("hub") and holds
// crypto:seal:console-* (and nothing for entre-textos).
const { ciphertext, partition } = await crypto.encrypt({
  key: 'console-flags',
  plaintext: command,
  aad,
  partition: 'entre-textos',
})
// entre-textos opens it with its own token: decrypting a console-* key of its own
// partition needs no grant (see below).
```

- **Encrypt only.** Every other operation (`decrypt`, `rewrap`, `datakeys`, `sign`, `verify`,
  `hmac`, keys, export) refuses a partition other than the token's (`403`).
- **An explicit grant.** The caller's token needs `crypto:seal:<key>` (prefix wildcards work:
  `crypto:seal:console-*`). `crypto:encrypt:<key>` and `crypto:*` are not enough, so a tenant with
  every right over its own partition cannot forge ciphertext another app trusts.
- **Audited where the key lives.** The `encrypt` row is written in the target partition, with the
  caller's actor, its client id (or `partition:<caller>`) as the client and `metadata.sealedFrom`;
  a refusal is written in the caller's partition.
- **Apps open their own console keys.** A verified token for partition `P` may `decrypt` with any
  key named `console-*` **in `P`** without a grant: implicit, decrypt only (never encrypt, manage,
  rewrap or export), never another partition's, and nothing else widens (the token's explicit
  capabilities still decide every other key). The seal grant stays explicit: it is what stops one
  app forging commands to another.
- **Console keys provision themselves.** When the key is missing in the target partition and its
  name starts with `console-`, the server creates it there (`aes256-gcm`) and seals: the Agora
  consoles' keys exist after the first command, with no `crypto:keys:manage` grant anywhere. Only
  on this path, only for `console-*` names, only `aes256-gcm` (decrypt never creates). Two seals
  at once create one key. The creation is audited in the target partition, with the sealing
  caller as the actor and `metadata.provisionedBy: 'seal'`. Turn it off with
  `sealProvisioning: false` in the server's `config/crypto.ts`.
- **Clear failures.** Any other missing key (or a console key with `sealProvisioning: false`)
  answers `404` with the exact `node ace crypto:keys:create <key> --type aes256-gcm --application
  <partition>` to run.
- **Older servers.** The result echoes `partition`; `CryptoClient` and the broker transport throw
  a clear error ("upgrade @adonis-agora/crypto on the crypto server, or configure `crypto`
  explicitly") when a server that predates the field ignored it, instead of returning a ciphertext
  nobody can open.

Same over HTTP (`POST /v1/encrypt` with `partition` in the body), the broker transports and the
in-process service.

## Who is recorded

The audit trail records `actor ?? clientId ?? partition`:

- with authkit, a token exchange for a person carries `act` (RFC 8693) and the verifier reports that
  `sub` as `actor`; a pure service client has none, so its `client_id` is recorded;
- with a shared secret, the partition, or the `actor` you configured.

Authorization always uses the token's own capabilities — never the actor's.

An operation can also carry **`context`**: a short label for *what* the open was for (`user:42`,
`grant:7`, `boot`, `config:streaming:production:db.password`). It is not encrypted, so never put the
plaintext or a secret in it; it lands on the audit row as `metadata.context`, refusals included. The
crypto server only knows the label you send — the app is the one that knows which person is behind it.

## Refusals

| Case | Status | Code |
| --- | --- | --- |
| no token, unknown secret, expired token | `401` | `unauthenticated` |
| token without the capability for this key/operation | `403` | `forbidden` |
| key does not exist in this app | `404` | `not_found` |

A refused operation is audited (`result: 'denied'`) with the capability it was missing, so "who
tried" is answerable after the fact.
